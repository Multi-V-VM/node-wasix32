# Design: Turbofan→wasm backend for the node-wasix32 V8 port

**Date:** 2026-06-14
**Status:** Approved (design); implementation plan pending
**Scope:** Make V8 builtins executable on the `wasm32`/WASI port of Node so that
JavaScript can actually run. Covers the dispatch/calling-convention model, the
code-generator that lowers V8 machine IR to wasm bytecode, and the build
pipeline that produces and links the generated builtins into `node.wasm`.

---

## 1. Problem & context

The port builds `node.wasm` (Node + V8 targeting a synthetic `V8_TARGET_ARCH_WASM32`,
toolchain `/opt/wasi-sdk`, run under `wasmer`). After a long series of stub fixes,
startup now proceeds through isolate/heap/context bootstrap and JS *compilation*,
then traps on the **first JS execution**:

```
RuntimeError: undefined element: out of bounds table access
  at v8::internal::Invoke ... → Execution::Call → InitializePrimordials
```

Root cause is architectural, not a stub bug:

- There is **no wasm codegen backend**: `assembler-wasm32.cc` is a stub (`nop`
  emits a placeholder byte); `compiler/backend/wasm32/` has only an
  `instruction-codes` header, no instruction-selector / code-generator.
- Every builtin path in `setup-builtins-internal.cc` produces empty/placeholder
  code on WASI: `Generate_*` (ASM) are empty, the CSA/Torque builtins
  (TFJ/TFC/TFS/TFH) and bytecode handlers (BCH) go through a scheduler that does
  nothing, and even CPP builtins go through an empty `Generate_Adaptor`.
- `GeneratedCode::Call` (USE_SIMULATOR is **not** defined for wasm32) does
  `fn_ptr_(args...)` where `fn_ptr_ = reinterpret_cast<Signature*>(code->instruction_start())`.
  On wasm a function pointer is an `__indirect_function_table` index, but
  `instruction_start()` returns a pointer into the embedded **data** blob → the
  `call_indirect` traps with "undefined element: out of bounds table access".

**Goal:** builtins become real wasm functions reachable via `call_indirect`, with
`Code::instruction_start()` returning a valid funcref index, generated by lowering
V8's existing CSA/Turboshaft IR to wasm bytecode at build time.

Non-goals (v1): performance/optimization, natural-loop reconstruction, the
optimizing JS tier (Maglev/Turbofan-for-JS), wasm SIMD, multi-isolate/threads.

Related notes: see memory `wasm32-builtin-execution-gap`, `wasi-v8-handle-scheme`,
`node-wasix-build-process`.

## 2. Dispatch & calling-convention model (foundation)

**Decision: emulated register file in linear memory + uniform `call_indirect`
signature, reusing V8's simulator ABI plumbing.**

- A global `Address g_regs[N]` in **linear memory** is the ABI. V8's "registers"
  (root register, context, the per-`CallInterfaceDescriptor` argument registers,
  return slot) are fixed slots in `g_regs`.
- **Every generated builtin is a wasm function of one uniform signature**
  (`void()` reading args from / writing results to `g_regs`). `call_indirect`
  therefore always type-checks — the per-descriptor signature-matching problem
  disappears.
- `GeneratedCode::Call(args...)` (wasm path) marshals C++ args into `g_regs` per
  the calling convention, performs the `call_indirect`, then reads the return
  slot. This is the same shape as V8's existing simulator `Call`; we model wasm
  as a "simulator target" and reuse the `USE_SIMULATOR` plumbing (arg
  marshalling, `RedirectExternalReference` for C calls, GC integration), except
  generated code runs as **native wasm functions** rather than being interpreted.
- Inter-builtin calls inside generated code lower to "write args to `g_regs`;
  `call_indirect`; read result from `g_regs`".
- `Code::instruction_start(builtin)` returns the bits of a real function pointer
  (`&generated_builtin`) — which on wasm *is* its `__indirect_function_table`
  index — so the existing `reinterpret_cast<Signature*>(addr)` dispatch recovers
  the correct funcref unchanged.

This single mechanism collapses the signature, calling-convention, and
root-register problems into one tractable ABI, and is shared by any future
interpreter path, so none of it is throwaway.

### 2.1 Register file is linear memory, not wasm locals (GC requirement)

GC scans **linear memory only**; it cannot see wasm locals (VM-internal value
stack). Therefore `g_regs` slots and all register-allocator spill slots are
**linear-memory locations**. wasm locals are used only as ephemeral, untagged,
single-instruction scratch (load slot → compute → store slot). Consequently every
location V8's register allocator assigns — register or spill — is in linear memory
and is GC-scannable. This is what makes precise safepoint maps (§3.4) work and
removes any register/local duality for tagged values.

## 3. Code-generator: V8 machine IR → wasm bytecode

Reuse the entire V8 backend pipeline and replace only the two arch-specific
leaves:

```
Turboshaft/Turbofan graph → schedule → InstructionSelector(wasm32)
  → InstructionSequence → RegisterAllocator → CodeGenerator(wasm32) → wasm bytecode
```

### 3.1 Register model

Define a fixed physical register set (initial target: 16 GP + 16 FP) in
`register-wasm32.h`, each backed by a `g_regs` slot. V8's register allocator runs
**unchanged**; spills become loads/stores against the emulated stack in linear
memory. Straight-line code is `local.get / op / local.set` over ephemeral wasm
locals that shadow the slots for the duration of a single lowered instruction.
(Using wasm's operand stack directly to avoid load/store churn is an explicit
later optimization, not a correctness requirement.)

### 3.2 `instruction-selector-wasm32.cc`

Map V8 machine IR opcodes to the `kWasm32_*` instruction codes
(`instruction-codes-wasm32.h`), following the structure of existing arch
selectors. Cover the integer/float/memory/compare/branch opcodes that the
CSA/Torque builtins and bytecode handlers actually use. The Turbofan/Turboshaft
selector adapter is shared, so one selector covers both IRs. Calling-convention
slot assignment is driven by `interface-descriptors-wasm32-inl.h` (already
present) as the single source of truth, shared with hand-written builtins.

### 3.3 `code-generator-wasm32.cc`

- **Straight-line ops:** lower each `Instruction` to wasm opcodes over the
  register-slots.
- **CFG structuring — dispatch-loop relooper (v1).** V8's `InstructionSequence`
  has blocks with arbitrary successors; wasm allows only structured control flow.
  v1 uses the always-correct construction: one `loop` wrapping nested `block`s,
  a `br_table` at entry selecting the current block from a `$label` local, and
  every branch lowering to `local.set $label K; br $loop`. Handles arbitrary
  CFGs (including irreducible loops and handler edges). Natural-loop
  reconstruction is a later optimization.
- **Frames:** V8 frame ops (push/pop, `[sp+off]`) lower to loads/stores against
  an emulated stack-pointer global in linear memory.
- **Calls:** code/builtin calls → marshal args into `g_regs` per the descriptor,
  `call_indirect` (uniform signature), read return slot. C-runtime calls go
  through a hand-written `CEntry` builtin that invokes the `Runtime_*` function
  pointer (reusing the simulator `RedirectExternalReference` shim).

### 3.4 Precise safepoints & GC

v1 emits **precise** safepoint maps from the start (not conservative). Reuse V8's
existing `SafepointTableBuilder` and the register allocator's `ReferenceMaps`:
at each safepoint (call / GC-triggering point) record exactly which `g_regs` /
stack slots hold live tagged pointers. Because all those slots are in linear
memory (§2.1), GC maps the recorded indices to linear-memory addresses and scans
precisely. This is the principal correctness mechanism for heap integrity.

### 3.5 Wasm encoder

A small, self-contained bytecode emitter (LEB128, opcode tables, locals/type/
function/code sections) that the CodeGenerator writes into — one wasm function
body per builtin. Testable in isolation against `wasm-validate`.

### 3.6 Risks

- **GC/safepoint correctness** across the emulated frames — highest-risk area;
  mitigated by precise maps + linear-memory-only locations, but needs heavy
  verification.
- **CFG edge cases** — critical edges, loop headers, exception-handler edges in
  the dispatch-loop construction.
- **Calling-convention agreement** — hand-written builtins (JSEntry, CEntry) and
  generated ones must assign identical `g_regs` slots per descriptor.

## 4. Build pipeline

**Constraint:** builtins must end up as wasm functions *inside* `node.wasm` (no
runtime wasm instantiation available in the wasmer/WASI embedding), and
`mksnapshot` is itself wasm (cannot run on the host). The build is therefore
staged.

### 4.1 Phase 1 — generate

Build `mksnapshot.wasm` containing the new codegen backend and run it **under
wasmer** during the build. It executes V8's `SetupBuiltinsInternal`, lowering each
builtin to wasm bytecode. Outputs:

- (a) the builtin function bodies + a `Builtin → function-index` table, and
- (b) the V8 startup snapshot blob (heap + `Code` objects that reference builtins
  **by id**, not by address — this is what avoids the chicken-and-egg between
  generation and final link).

**Feasibility checkpoint:** builtin generation is pure C++ IR-building and must
not itself execute JS; `mksnapshot.wasm` must complete a full generation pass
under wasmer without hitting the builtin-execution gap. This is the key go/no-go
gate for the whole approach and should be proven early.

### 4.2 Phase 2 — merge/link

Emit the generated builtins as a **wasm object file (`.o`)** and let `wasm-ld`
link them into the final `node.wasm`. (Alternative considered: emit a standalone
module and fuse it with Binaryen `wasm-merge`; rejected for v1 to stay inside the
existing wasi-sdk toolchain and avoid a Binaryen build dependency.)

### 4.3 Phase 3 — wire

- The `Builtin → funcref` table is emitted as data that `node.wasm` reads at
  startup; `Code::instruction_start(builtin)` returns `&builtin_fn` (its funcref
  index).
- The snapshot blob replaces `node_snapshot_stub.cc` as embedded data; at startup
  V8 deserializes it and `SetInstructionStartForOffHeapBuiltin` resolves each
  builtin's instruction_start from the funcref table.
- This flips the build from **no-snapshot mode to snapshot mode**.

### 4.4 Risk

The `.o` emission + relink with stable funcref indices is the fiddly part;
id-based (not address-based) snapshot references resolved at startup keep the
indices from needing to be known at generation time.

## 5. Hand-written bootstrap builtins

A small set cannot come from the CSA pipeline because they *are* the entry/exit
glue. These get real hand-written implementations in `builtins-wasm32.cc`
(currently all empty stubs), following the `g_regs` ABI:

- `JSEntry`, `JSConstructEntry`, `JSRunMicrotasksEntry`
- `CEntry` (calls into `Runtime_*` C++ functions)
- Deopt entries
- `InterpreterEntryTrampoline` + bytecode-handler dispatch entry

Everything else (CSA/Torque builtins, the ~200 bytecode handlers) is
codegen-generated via §3.

## 6. Components & interfaces (summary)

| Component | Purpose | Depends on |
|-----------|---------|-----------|
| `g_regs` register file + wasm `GeneratedCode::Call` path | ABI between C++ and generated builtins; dispatch via `call_indirect` | simulator plumbing, `interface-descriptors-wasm32` |
| `register-wasm32.h` | physical register set mapped to `g_regs` slots | §2.1 |
| `instruction-selector-wasm32.cc` | V8 machine IR → `kWasm32_*` codes | `instruction-codes-wasm32.h`, interface descriptors |
| `code-generator-wasm32.cc` | `kWasm32_*` → wasm bytecode; CFG structuring; frames; calls; safepoints | wasm encoder, `SafepointTableBuilder` |
| wasm encoder | emit valid wasm function bodies | — |
| `builtins-wasm32.cc` | hand-written bootstrap builtins | `g_regs` ABI |
| build pipeline (makefile + mksnapshot-under-wasmer + `.o` link) | produce & link generated builtins; embed snapshot | wasm-ld, wasmer, all of the above |
| startup wiring (`instruction_start`, snapshot deserialize) | resolve builtins by id → funcref at runtime | funcref table, snapshot blob |

## 7. Validation milestones (incremental)

1. **Dispatch spine:** one hand-written `g_regs`-ABI builtin reachable via
   `call_indirect`; `instruction_start` returns its funcref; a C++ call succeeds.
2. **JSEntry hand-written:** `Invoke` enters and returns from a trivial frame
   without the table-access trap.
3. **Encoder + code-generator on one CSA builtin:** generate one simple builtin
   as wasm, validate with `wasm-validate`, dispatch to it.
4. **mksnapshot-under-wasmer feasibility gate (§4.1):** full generation pass
   completes without executing JS.
5. **Interpreter path:** `InterpreterEntryTrampoline` + bytecode handlers
   generated; a trivial JS function runs.
6. **Primordials:** `InitializePrimordials` completes; `node -e "console.log(...)"`
   prints. End-to-end smoke test passes.

---

## 8. Testing strategy

- **Unit:** wasm encoder output validated with `wasm-validate`; instruction
  selector golden tests for opcode coverage; CFG-structuring tests on synthetic
  irreducible/critical-edge graphs.
- **Integration:** per-milestone smoke runs under `wasmer` (filter the
  `HashSeed:`/`Eternalize:` debug spam per `node-wasix-build-process`).
- **GC stress:** run with aggressive GC flags once the interpreter path works, to
  shake out safepoint-map bugs early.
- **Differential:** compare generated-builtin behavior against the C++ `Runtime_*`
  equivalents where they exist.
